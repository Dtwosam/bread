## Real gaps demonstrated and repaired

### 1. Active graduation status misclassified as Processing

Canonical indexed launch state uses `graduationPhase = NOT_GRADUATED` before graduation readiness. The previous UI classified every non-null phase string as Processing, so ordinary active launches could display the wrong user-facing state.

RED:

- head `07be2ad31ffbe660763352c06ea4fd383d4638c7`;
- Day-7 Token-page workflow `31414672664`;
- 13 retained tests passed and only the new active-graduation classification assertion failed.

Minimum GREEN:

- `apps/web/components/token/graduation-module.tsx` now keeps `NOT_GRADUATED` + not-ready state Active;
- `readyToGraduate` or later non-`NOT_GRADUATED` phases remain Processing unless failure/lock evidence establishes Pending/Graduated.

This is presentation classification only. It does not change indexer graduation state, readiness, protocol graduation semantics, or financial authority.

### 2. Persisted trade recovery was not visible in the token trade panel after refresh

The existing global provider already recovered canonical persisted transaction records, but the token `TradeExperience` initialized a separate visible `IDLE` state and did not consume the recovered state. A refresh could therefore visually reopen a fresh trade surface while global recovery was still resolving the saved transaction.

RED:

- head `5d7be6164f5f3a48024a34d9fb3e9386dac9fe2b`;
- Task-10 workflow `31416163954`;
- 18 browser tests passed and only the new recovery-lock regression failed because the persisted `CONFIRMING` Buy rendered as visible `IDLE`.

Minimum GREEN:

- `trade-runtime.tsx` exposes recovered trade states;
- `wallet-trade-provider.tsx` publishes BUY/SELL states produced by the existing `recoverPersistedTransactions` owner;
- `trade-experience.tsx` adopts the matching recovered state and follows same-hash recovery updates.

No new receipt polling algorithm, storage key/schema, transaction builder, simulation authority, wallet-send path, or confirmation semantics were introduced.

### 3. Fast terminal recovery could race visible state back to IDLE

The first evidence-bearing run was technically successful but Playwright classified the reload-to-confirm recovery test as flaky: its first attempt observed `IDLE`, while the retry observed `CONFIRMED`. This was not accepted as a closeout PASS.

Demonstrated evidence:

- evidence head `debf4f3fe73e260e0076370918a2e973396fb9b2`;
- Task-10 run `31418396796`;
- the saved transaction could move from recovery to terminal state before `TradeExperience` adopted the intermediate locked state, leaving the visible panel at its fresh `IDLE` initialization on that scheduling path.

Minimum GREEN:

- `TradeExperience` records the recovered hash it has adopted;
- the first recovered hash is adopted once from `IDLE` even when recovery reaches a terminal state before the intermediate render;
- same-hash updates continue to be adopted;
- a previously adopted terminal hash is not re-adopted after the user intentionally begins a new trade state.
